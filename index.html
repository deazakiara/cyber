Platform 1: TCP SYN flood

Filling a server's waiting list with connections that never finish

Slides 44 to 46

Every TCP connection opens with a . The server sets aside memory for the connection, a , as soon as the first packet arrives, before it knows the sender is real. A SYN flood sends thousands of first packets from addresses. Each leaves a connection waiting for an answer that never comes, until the is full and real users are turned away.

How EHE defines itA attack makes a computer or network partly or wholly unavailable to the people entitled to use it, by overloading it with requests or traffic that serve no real purpose EHE p. 28. The SYN flood is the technique that does this through the TCP three-way handshake EHE p. 36. The courseware's general picture of a DoS shows attack traffic using up all the bandwidth. A SYN flood needs far less: it aims at the queue of one listening port, not at the capacity of the network RFC 4987 §1.

Spotting it on a serverCount half-open connections with netstat -an | grep SYN_RECV | wc -l; the model's board footer shows the same count. The slide treats more than 100 as an early sign of a SYN flood (slide 58). On Linux each SYN_RECV entry costs about 304 bytes of memory kernel docs.

Finding who is sendingSlide 58's second command counts connections per source address: netstat -ntu | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -n. Against a spoofed flood it finds nothing useful, because every SYN carries a different fake address, so each one appears once, as on the model's board. It helps against a botnet that floods from its real addresses, where a few sources show up hundreds of times.

What sets the SYN flood apartFour of the other five win by volume: they send more than the target or its link can carry or process. The SYN flood wins by holding state. Each SYN is a tiny packet, but it occupies a queue slot for as long as the server keeps retrying, about 63 s on Linux by default kernel docs. That is why Model 1 fills up at only 5 SYNs per second, and why the lecture measures this kind of attack in packets per second, not gigabits (slide 55). EHE states the layer only for the HTTP flood; the other rows are placed by the protocol they use.

Platform 2: Mirai botnet and the DGA

How cameras and routers with factory passwords became one remote-controlled botnet

Slides 51 and 52

In 2016 Mirai took over about 600,000 cameras, video recorders and routers at its peak Antonakakis §4.2, just by logging in over with factory-default passwords. The infected devices formed a that flooded targets on orders from a server. The bots only find victims; a separate loader server does the infecting §2.

Slide 52 puts Mirai and DGA together. They came at different times.The 2016 Mirai reached its C2 through domain names written into its code, and researchers pulled 67 of them out of the binaries §3.3. A appeared later in one short-lived variant, used only when those hardcoded domains failed to resolve Netlab, Dec 2016. The two models below keep them apart.

Two numbers that differ from slide 52The slide gives about 60 default logins and "millions" of devices. The Mirai source code holds 62 username and password pairs, and the measured peak was about 600,000 devices at once Antonakakis §2, §4.2. The slide also describes DGAs that make thousands of names a day; that is true of DGAs in general, while the Mirai variant made one Netlab.

The courseware does not name Mirai. It describes any DDoS botnet with three roles and three steps EHE p. 29.

Platform 3: TCP session hijacking in 3 phases

Taking over a live connection by forging the numbers it trusts

Slides 63 to 66

Once a TCP connection is open, each end accepts any packet with the right addresses, ports and numbers. Nothing else proves who sent it. An attacker between client and server can read those numbers, knock the two ends out of step, then speak to the server as the client Joncheray 1995.

How EHE defines itSession hijacking is taking over an established, valid TCP session between a client and a server. By sniffing the traffic, or by stealing or guessing the , the attacker acts as the user who has already logged in. The attacker can also simply break the session, which is a denial of service EHE p. 45. Model 4 shows both outcomes: with no protection the attacker issues a command as the client, and with TLS on the most it can do is make the server close the connection.

Two ways to desynchronizeThe model injects harmless null data (Telnet no-ops) into an open session, so the server's count jumps ahead of the client's. The other way, early desync, strikes during setup: the attacker resets the half-built connection with an and opens a new one with a different starting number Joncheray. Either way the result is the same state, and an follows.

Spotting itA network IDS sees what the packet log in the model shows: a sudden jump in a connection's sequence numbers (the "SEQ Jump" indicator on slide 80) and bursts of empty ACKs going back and forth between two hosts. The lab tool on slides 66 and 67, Hunt, does the same three phases on a real LAN: it lists active connections, resets or desynchronizes one, and injects into it.

Getting on the path: the sniffing part of the module

Phase 1 needs the attacker to see the packets. The first part of the courseware explains how. A sniffer puts the network card into , so it reads every packet on the wire and not only those addressed to it EHE p. 6. On a hub that is enough. On a switch each machine receives only its own traffic, so the attacker has to interfere EHE p. 7.

Passive sniffingActive sniffing

On a switched network the usual route is . ARP links an IP address to a hardware (MAC) address. The attacker sends forged ARP entries to the victim, so traffic meant for the legitimate address goes to the attacker's machine instead EHE p. 13. EHE gives the whole route in six steps EHE p. 8:

  1. Connect a machine to a switch port.
  2. Run discovery tools to learn how the network is laid out.
  3. Pick the victim's machine.
  4. Poison the victim's ARP cache.
  5. Traffic meant for the victim is now redirected through the attacker.
  6. Read the sensitive data out of the redirected traffic.

Step 5 is where Model 4 startsThe model opens with the attacker already on the path. EHE also lists Telnet among the protocols that send everything in plaintext, keystrokes, usernames and passwords included EHE p. 9, which is why the model's victim is a Telnet session.

Stopping it at this stageRestrict physical access to network devices. Use end-to-end encryption such as HTTPS, TLS or a VPN. Add the gateway's MAC address to the ARP cache permanently, or use static ARP tables, so forged entries are ignored EHE p. 21.

Finding a snifferEHE gives three tests. Ping method: send a ping with the suspect's correct IP address but a wrong MAC address; only a card in promiscuous mode answers EHE p. 22. DNS method: watch for a machine that makes many reverse DNS lookups, as most sniffers do to turn addresses into names p. 23. ARP method: a promiscuous machine has already cached everyone's ARP details and replies to a ping directly, where a normal machine sends an ARP probe first p. 24.

The three packets (SYN, SYN/ACK, ACK) that open a TCP connection before any data moves. RFC 9293 §3.5
TCB
Transmission Control Block: the record a host keeps in memory for each connection, holding its addresses, ports, sequence numbers and state. RFC 9293 §3.3.1
Half-open connection (SYN_RECV)
A connection the server has answered with SYN/ACK but that has not received the final ACK yet. RFC 4987 §2.2
Backlog (SYN queue)
The limit on how many half-open connections a listening port holds. When it is full, new SYNs are dropped. RFC 4987 §2.2
IP spoofing
Writing a false source address into a packet, so the replies go somewhere else. RFC 4987 §2.2
RST
A TCP flag that aborts a connection at once. A host sends it when a packet does not belong to any connection it knows. RFC 9293 §3.5.2
SYN cookie
A sequence number the server builds from a time counter, the client's MSS and a keyed hash of both addresses and ports, so it can store nothing until a valid ACK returns it. Bernstein
ISN
Initial Sequence Number: each side's starting count. It must be hard to predict, or an attacker off the path can guess it. RFC 6528 §3
SEQ and ACK numbers
SEQ numbers the bytes a side sends; ACK names the next byte it expects. A segment is accepted only if its SEQ falls inside the receiver's window. RFC 9293 §3.4
Botnet
A group of malware-infected devices controlled remotely as one. CISA TA16-288A
C2 (command and control)
The server an operator uses to send orders to infected devices. MITRE ATT&CK
Telnet
An old remote-login protocol that sends everything, passwords included, unencrypted. Mirai scanned for it on TCP ports 23 and 2323. Antonakakis §2
DGA
Domain Generation Algorithm: code that malware and its operator both run to compute the same changing list of C2 domain names, usually from the date. ATT&CK T1568.002
NXDOMAIN
The DNS answer that means the name does not exist. Many of them from one machine is a sign of a DGA at work. ATT&CK T1568.002
Sinkhole
Defenders take control of a C2 name and point it at their own server. Bots that connect there are cut off from the operator and reveal themselves. ATT&CK T1568.002
On-path attacker
Also called man-in-the-middle: an attacker on the route between two hosts, who can see their packets and send forged ones, such as someone on the same Wi-Fi or a compromised router. Joncheray
Desynchronized state
Both ends think the connection is open, but each one's SEQ falls outside what the other expects, so their own packets get rejected. Joncheray
ACK storm
Two desynchronized ends answering each other's unacceptable packets with ACKs, in a loop. The ACKs carry no data, so one lost packet ends it. Joncheray
TLS and IPsec ESP
TLS encrypts and authenticates the data inside a TCP connection; ESP does the same for whole IP payloads, TCP header included. Forged bytes fail their integrity checks. RFC 8446 RFC 4303
DoS (denial of service)
An attack that makes a computer or network unavailable to its legitimate users by overloading it with requests or traffic. EHE p. 28
DDoS (distributed denial of service)
A coordinated denial-of-service attack launched from a large number of compromised systems at once. EHE p. 29
Handler and zombie
EHE's names for the two layers of a DDoS. The handler is the system the attacker sets up and controls directly; the zombies are the compromised machines it instructs to attack. Zombies are also called bots. EHE p. 29
Promiscuous mode
A network card setting in which the card reads every packet on the wire, not only those addressed to its own MAC address. Sniffers depend on it. EHE p. 6
ARP spoofing
Sending forged ARP entries to a machine, so that it links a legitimate IP address to the attacker's MAC address and sends that traffic to the attacker. Also called ARP poisoning. EHE p. 13
Session ID (session token)
A value a web server creates to tell one client's session from another. Whoever presents it is treated as that logged-in user. EHE p. 45
IDPS
Intrusion detection or prevention system. It monitors network traffic continuously, alerts when packets match a known attack signature, and can block them. EHE p. 58
HSTS
HTTP Strict Transport Security: a response header that tells the browser to use only HTTPS for that site (slide 78). EHE lists it as a session hijacking countermeasure. EHE p. 59
