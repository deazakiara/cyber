Platform 1: TCP SYN flood

Filling a server's waiting list with connections that never finish

Key sources: RFC 4987, RFC 9293

Every TCP connection opens with a . The server sets aside memory for the connection, a , as soon as the first packet arrives, before it knows the sender is real. A SYN flood sends thousands of first packets from addresses. Each leaves a connection waiting for an answer that never comes, until the is full and real users are turned away.

What kind of attack it isA SYN flood is a attack: it makes a computer or network partly or wholly unavailable to the people entitled to use it, by overloading it with requests or traffic that serve no real purpose Module 07 p. 28. The usual picture of a DoS is attack traffic using up all the bandwidth. A SYN flood needs far less, because it aims at the queue of one listening port, not at the capacity of the network RFC 4987 §1.

Four stages or five stepsThe four-stage view starts counting at the first spoofed packet, so its stages are steps 2 to 5 here. Why the server's reply goes unanswered is explained in the note under the next table.

Why the fake addresses must be offlineIf a spoofed address belonged to a live machine, that machine would answer the unexpected SYN/ACK with a , and the server would free the slot at once RFC 4987 §2.2.

Spotting it on a serverCount half-open connections with netstat -an | grep SYN_RECV | wc -l; the model's board footer shows the same count. There is no fixed threshold: compare the count with what the server normally shows, because a busy server holds many legitimate half-open connections. On Linux each SYN_RECV entry costs about 304 bytes of memory kernel docs.

Finding who is sendingA second command counts connections per source address: netstat -ntu | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -n. Against a spoofed flood it finds nothing useful, because every SYN carries a different fake address, so each one appears once, as on the model's board. It helps against a botnet that floods from its real addresses, where a few sources show up hundreds of times.

DoS vs DDoS

Model 1 is a DoS: one attacker against one server. When the same flood comes from a it is a , which is where platform 2 picks up Module 07 p. 30.

AspectDoSDDoS
ScaleSmall, usually one machine or service affectedLarge, many machines or services affected
Cost and resourcesLow: one attacking system is enoughHigh: many systems are needed, such as a botnet
How it overloadsFrom one placeFrom several locations at once
MitigationEasier, because there is one source to blockHarder, because the traffic comes from many sources
DurationUsually shorterCan last longer
Resources to prevent itFewerAdvanced infrastructure and specialized tools

One attack, both formsThe 2016 attack on Dyn was a DDoS that included SYN floods: the technique from this platform, sent by the botnet from the next one Antonakakis §6.3.

What sets the SYN flood apartUDP, ICMP and HTTP floods win by volume: they send more than the target or its link can carry or process Module 07 p. 33 to 35. The SYN flood wins by holding state. Each SYN is a tiny packet, but it occupies a queue slot for as long as the server keeps retrying, about 63 s on Linux by default kernel docs. That is why Model 1 fills up at only 5 SYNs per second, and why this kind of attack is measured in packets per second, not gigabits per second.

Defenses outside the serverTwo measures act before a spoofed SYN reaches the queue. Networks can stop packets with forged source addresses at the ISP level, which is the Filtering row above Module 07 p. 41. DDoS protection services such as Cloudflare, Akamai, Imperva, Radware DefensePro and F5 stand in front of the server and pass on only clean traffic, like the Firewall or proxy row Module 07 p. 42; cloud services usually announce the protected addresses over BGP anycast, so attack traffic is spread across many scrubbing centers. On the server itself, keep the kernel up to date Module 07 p. 41, because the SYN queue and SYN cookies are kernel code kernel docs.

Platform 2: Mirai botnet and the DGA

How cameras and routers with factory passwords became one remote-controlled botnet

Key source: Antonakakis et al. 2017

In 2016 Mirai took over about 600,000 cameras, video recorders and routers at its peak Antonakakis §4.2, just by logging in over with factory-default passwords. The infected devices formed a that flooded targets on orders from a server. The bots only find victims; a separate loader server does the infecting §2.

Mirai and DGAs are often mentioned together. They came at different times.The 2016 Mirai reached its C2 through domain names written into its code, and researchers pulled 67 of them out of the binaries §3.3. A appeared later in one short-lived variant, used only when those hardcoded domains failed to resolve Netlab, Dec 2016. The two models below keep them apart.

Two numbers that are often quoted wronglyMirai is often said to use about 60 default logins and to have infected "millions" of devices. The Mirai source code holds 62 username and password pairs, and the measured peak was about 600,000 devices at once Antonakakis §2, §4.2. DGAs are also often described as making thousands of names a day; that is true of DGAs in general, while the Mirai variant made one Netlab.

The general shape of a DDoS botnet, and how Mirai fits it

A DDoS botnet is usually described with three roles and three steps Module 07 p. 29.

  1. The attacker sets up a system.
  2. The handler infects a large number of computers over the internet.
  3. Those machines, the zombies, are instructed to attack the target server.
RoleIn the general modelIn Mirai
AttackerSets up the handlerThe operator, who runs the C2 and picks the targets

The difference that mattersIn the general model the handler does the infecting. In Mirai the zombies find the next victims themselves, so every new bot is one more scanner Antonakakis §2. Auto-spread in Model 2 shows the effect: the more bots there are, the faster the rest fall.

DefenseChanging default passwords and turning off Telnet stops the infection at the source. A reboot alone clears the malware from RAM, but an unchanged device is found and infected again CISA TA16-288A. Against a DGA, flag machines with many NXDOMAIN answers and sinkhole the predicted names ATT&CK T1568.002.

Spotting an infected deviceA bot scans for the next victim, so on your own network a camera or router that suddenly opens many outbound connections to TCP 23 and 2323 is probably infected Antonakakis §2. Block outbound Telnet from IoT devices at the firewall, so an infected one cannot recruit others.

When the order comesStop 6 of Model 2 ends with the bot waiting for attack orders. Mirai carries ten attack types, among them HTTP, UDP, SYN and ACK floods. Its bots mostly sent traffic directly: only 2.8% of attack commands used amplification Antonakakis §6.1.

Where platforms 1 and 2 meetA SYN flood from one machine is a DoS, and filtering forged source addresses can blunt it. The same flood from hundreds of thousands of bots is a DDoS sent from real addresses, so that filter no longer helps RFC 4987 §3.1. This is the Mitigation row of the DoS vs DDoS table in practice.

Platform 3: TCP session hijacking in 3 phases

Taking over a live connection by forging the numbers it trusts

Key sources: Joncheray 1995, RFC 9293

Once a TCP connection is open, each end accepts any packet with the right addresses, ports and numbers. Nothing else proves who sent it. An attacker between client and server can read those numbers, knock the two ends out of step, then speak to the server as the client Joncheray 1995.

What it isSession hijacking is taking over an established, valid TCP session between a client and a server. By sniffing the traffic and obtaining what identifies the session, the attacker acts as the user who has already logged in. The attacker can also simply break the session, which is a denial of service Module 07 p. 45. Model 4 shows both outcomes: with no protection the attacker issues a command as the client, and with TLS on the most it can do is make the server close the connection.

Two ways to desynchronizeThe model injects harmless null data (Telnet no-ops) into an open session, so the server's count jumps ahead of the client's. The other way, early desync, strikes during setup: the attacker resets the half-built connection with an and opens a new one with a different starting number Joncheray. Either way the result is the same state, and an follows.

Spotting itA network IDS sees what the packet log in the model shows: a sudden jump in a connection's sequence numbers and bursts of empty ACKs going back and forth between two hosts. The classic hijacking tool Hunt does the same three phases on a real LAN: it lists active connections, resets or desynchronizes one, and injects into it.

Read or predict?Step 2 speaks of predicting the sequence number. An attacker on the path does not have to: the numbers are in every TCP header, and Model 4 simply copies them. Prediction is what an attacker off the path must do, and unpredictable are the defense against that RFC 6528.

How the attacker gets on the pathPhase 1 needs the attacker to see the packets. A sniffer puts the network card into , so it reads every packet on the wire and not only those addressed to it Module 07 p. 6. On a switched network each machine receives only its own traffic, so the attacker first uses : forged ARP entries make the victim send traffic meant for the legitimate address to the attacker's machine instead Module 07 p. 13. That is the position Model 4 starts from. The victim in the model is a Telnet session because Telnet sends everything in plaintext, keystrokes, usernames and passwords included Module 07 p. 9.

Why it worksFour of the usual reasons session hijacking succeeds apply to a TCP session Module 07 p. 46. What identifies the session travels unprotected: SEQ and ACK are in the clear in every TCP header. The identifiers can be weak: a predictable ISN lets an attacker off the path guess them RFC 6528. A session that never times out can be attacked for as long as it stays open. And most countermeasures do not work without encryption, which Model 4 shows: with protection set to None, nothing stops the injection.

CountermeasuresUse SSH to create a secure channel in place of Telnet, and encrypt data in transit as part of defense in depth Module 07 p. 59. SSH, like TLS, encrypts the data and checks its integrity inside the TCP connection, so in Model 4 it would behave like the TLS setting.

Detection, by hand and automaticThere are two ways to detect a hijack Module 07 p. 58. By hand: capture traffic with a packet sniffer such as Wireshark and filter it for suspicious activity. Automatic: an watches the traffic all the time, raises an alert when packets match a known attack signature, and blocks them. Either one would see what the packet log in Model 4 shows: REJECT and BAD SEQ rows, and a burst of empty ACKs.

Terms

3-way handshake
The three packets (SYN, SYN/ACK, ACK) that open a TCP connection before any data moves. RFC 9293 §3.5
TCB
Transmission Control Block: the record a host keeps in memory for each connection, holding its addresses, ports, sequence numbers and state. RFC 9293 §3.3.1
Half-open connection (SYN_RECV)
A connection the server has answered with SYN/ACK but that has not received the final ACK yet. RFC 4987 §2.2
Backlog (SYN queue)
The limit on how many half-open connections a listening port holds. When it is full, new SYNs are dropped. RFC 4987 §2.2
IP spoofing
Writing a false source address into a packet, so the replies go somewhere else. RFC 4987 §2.2
RST
A TCP flag that aborts a connection at once. A host sends it when a packet does not belong to any connection it knows. RFC 9293 §3.5.2
SYN cookie
A sequence number the server builds from a time counter, the client's MSS and a keyed hash of both addresses and ports, so it can store nothing until a valid ACK returns it. Bernstein
ISN
Initial Sequence Number: each side's starting count. It must be hard to predict, or an attacker off the path can guess it. RFC 6528 §3
SEQ and ACK numbers
SEQ numbers the bytes a side sends; ACK names the next byte it expects. A segment is accepted only if its SEQ falls inside the receiver's window. RFC 9293 §3.4
Botnet
A group of malware-infected devices controlled remotely as one. CISA TA16-288A
C2 (command and control)
The server an operator uses to send orders to infected devices. MITRE ATT&CK
Telnet
An old remote-login protocol that sends everything, passwords included, unencrypted. Mirai scanned for it on TCP ports 23 and 2323. Antonakakis §2
DGA
Domain Generation Algorithm: code that malware and its operator both run to compute the same changing list of C2 domain names, usually from the date. ATT&CK T1568.002
NXDOMAIN
The DNS answer that means the name does not exist. Many of them from one machine is a sign of a DGA at work. ATT&CK T1568.002
Sinkhole
Defenders take control of a C2 name and point it at their own server. Bots that connect there are cut off from the operator and reveal themselves. ATT&CK T1568.002
On-path attacker
Also called man-in-the-middle: an attacker on the route between two hosts, who can see their packets and send forged ones, such as someone on the same Wi-Fi or a compromised router. Joncheray
Desynchronized state
Both ends think the connection is open, but each one's SEQ falls outside what the other expects, so their own packets get rejected. Joncheray
ACK storm
Two desynchronized ends answering each other's unacceptable packets with ACKs, in a loop. The ACKs carry no data, so one lost packet ends it. Joncheray
TLS and IPsec ESP
TLS encrypts and authenticates the data inside a TCP connection; ESP does the same for whole IP payloads, TCP header included. Forged bytes fail their integrity checks. RFC 8446 RFC 4303
DoS (denial of service)
An attack that makes a computer or network unavailable to its legitimate users by overloading it with requests or traffic. Module 07 p. 28
DDoS (distributed denial of service)
A coordinated denial-of-service attack launched from a large number of compromised systems at once. Module 07 p. 29
Handler and zombie
Names for the two layers of a DDoS botnet. The handler is the system the attacker sets up and controls directly; the zombies are the compromised machines it instructs to attack. Zombies are also called bots. Module 07 p. 29
Promiscuous mode
A network card setting in which the card reads every packet on the wire, not only those addressed to its own MAC address. Sniffers depend on it. Module 07 p. 6
ARP spoofing
Sending forged ARP entries to a machine, so that it links a legitimate IP address to the attacker's MAC address and sends that traffic to the attacker. Also called ARP poisoning. Module 07 p. 13
IDPS
Intrusion detection or prevention system. It monitors network traffic continuously, alerts when packets match a known attack signature, and can block them. Module 07 p. 58
